## Implementation Decisions

### Matching bug (REMOTE-01)
- **D-01:** Before treating this as a behavior fix, empirically verify whether `remote_map` is actually unreadable inside the `find ... -print0 | while ...; done` loop (rename-remote-files-1-match-remote.zsh:38-70). A quick zsh test run during this discussion (`typeset -A m; ... find | while read; print "${m[5]}"; done`) showed the array **is** readable and even writable across that loop — because in zsh, the last command in a pipeline runs in the *current* shell, not a subshell. This is the same misdiagnosis pattern found for LOCALFS-01/02 in Phase 1 (see `01-CONTEXT.md`, and the Phase 1 "Planning note" in `ROADMAP.md`). If research/planning confirms the array is already readable, ship the fix as **hardening** (convert to the process-substitution pattern already used elsewhere in the codebase, for consistency — not because it's broken), not as a functional bug fix. If a real defect is found (e.g. in the `jq`/`rclone` output parsing, not the shell scoping), fix that root cause instead.
- **D-02:** Size-collision handling (multiple remote files sharing a local file's size) stays as-is — no new warning, no change to which match wins (first-write-wins into `remote_map`, so whichever remote file was listed last for a given size). This trade-off is already acknowledged in the script's own comment ("could lead to collisions... but for JPGs it's usually safe") and isn't part of REMOTE-01's stated scope. Out of scope for this phase; not deferred as a future idea since the original author already made this call knowingly.

### Dependency checks (REMOTE-02)
- **D-03:** Add `command -v rclone` and `command -v jq` checks to `rename-remote-files-1-match-remote.zsh` only, near the top before first use — mirroring the existing `identify` check pattern in `dev/manga/number-pages.zsh:67-70` (clear message to stderr, `exit 1`). `rename-remote-files-2-rename-local.zsh` does not call `rclone` or `jq` anywhere in its body (it only sources shadow files and does `mkdir`/`mv`), so no dependency check is added there despite REMOTE-02's literal wording naming both scripts — interpreting the requirement as "each script checks what it actually uses."

### Shadow-file validation (REMOTE-03)
- **D-04:** When `MATCHED_REMOTE_PATH` or `ORIGINAL_LOCAL_PATH` is empty/unset after `source`-ing a shadow file (rename-remote-files-2-rename-local.zsh:21), skip that file with an `Error:`-prefixed message to stderr and continue processing the remaining shadow files — do not abort the whole run. This matches the script's existing convention one branch down (lines 39-40: "warning: file not found in sync dir" already warns-and-continues rather than aborting), so the new validation follows the same shape.
- **D-05:** Keep `source "$shadow_file"` as the loading mechanism; do not switch to `grep`/`awk` parsing. CONCERNS.md flags `source` on a shadow file as an arbitrary-code-execution risk if the file is malformed/malicious, but shadow files here are self-generated by script 1 in the same trusted single-user workflow (not attacker- or third-party-controlled) — swapping the parsing mechanism is unrequested scope growth beyond REMOTE-03's literal ask ("validates that ... variables are set"). Only the presence/non-empty check is added.

### Remote config (REMOTE-04)
- **D-06:** Move `REMOTE_NAME` and `REMOTE_PATH` (rename-remote-files-1-match-remote.zsh:3-6) to environment variables, required with no hardcoded default. If either is unset when the script runs, fail fast with a clear stderr message and `exit 1` — same fail-fast convention as D-03's dependency checks, not a silent fallback to the old hardcoded values.

### Claude's Discretion
- Exact env var names — default to keeping the existing identifiers `REMOTE_NAME` / `REMOTE_PATH` unprefixed (matches current script variable names, minimal diff) unless research surfaces a collision risk with common env var names.
- Exact fix mechanism for D-01 if a real bug is confirmed (process substitution vs. other) — prefer process substitution for consistency with the Phase 1 precedent (`01-CONTEXT.md` "Claude's Discretion").
- Test coverage for these fixes: per the project-wide policy in `PROJECT.md` §Constraints (Testing), each fix needs a tracked test file, following the manual assert-style pattern from `dev/local-filesys/tests/test-retain-dir-struct.zsh` (no bats). Test scope/fixtures are Claude's discretion at planning time.
