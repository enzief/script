<objective>
Make `rename-remote-files-2-rename-local.zsh` refuse to act on a shadow file that does not
describe a file, and extend the phase-3 suite to cover the edges the reversion path can
actually hit.

Purpose: script 2 sources each shadow file and then moves a real file to the absolute path it
finds inside. Today a shadow file that sets nothing at all sails straight through — and
because the loop body runs in the current shell, the variables from the *previous* shadow file
are still in scope, so the move is driven by another file's paths rather than by empty ones.
That is a silent wrong-file relocation of irreplaceable data, and it is the failure mode
REMOTE-03 exists to close.

Output: `rename-remote-files-2-rename-local.zsh` with a per-iteration variable reset and a
non-empty validation that skips malformed shadow files without aborting the run, plus
malformed-shadow, stale-inheritance, empty-input, and re-run coverage in
`dev/remote/tests/test-rename-remote-files.zsh`.
</objective>

<environment_finding>
**A presence check alone is not enough: sourced variables survive from one loop iteration to
the next.** Verified empirically during planning (zsh 5.9), and this is the finding that shapes
Task 1.

`rename-remote-files-2-rename-local.zsh` loads each shadow file with `source` inside a
`find … | while` loop. In zsh the last element of a pipeline runs in the current shell, so
every iteration shares one variable scope. A reproduction of the exact loop shape over two
shadow files — one well-formed, one setting nothing — printed:

```
file=one.txt  MATCHED_REMOTE_PATH=[remote/real.jpg]  ORIGINAL_LOCAL_PATH=[/orig/real.jpg]
file=two.txt  MATCHED_REMOTE_PATH=[remote/real.jpg]  ORIGINAL_LOCAL_PATH=[/orig/real.jpg]
```

The malformed file inherited the previous file's values verbatim. A bare emptiness test would
have found both variables non-empty and waved it through. Adding `unset` for both variables at
the top of each iteration made the same loop print the well-formed file normally and skip the
malformed one:

```
file=one.txt  MATCHED_REMOTE_PATH=[remote/real.jpg]
Error: shadow file missing required variables, skipping: two.txt
```

So the reset is not defensive garnish — without it the validation REMOTE-03 asks for is
vacuous from the second iteration onward. `continue` was also confirmed to work correctly in
this loop shape, skipping one file and proceeding to the next.

**Script 2 does not call `rclone` or `jq` anywhere in its body** — only `find`, `source`,
`realpath`, `mkdir` and `mv`. That is why D-03 adds no dependency check here, diverging from
the literal wording of ROADMAP Phase 3 success criterion 2, which names both scripts.
</environment_finding>
